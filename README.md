# Zhynzher_nosql_1  MongoDB, Spotify датасет

Домашнє завдання з NoSQL. Беремо датасет Spotify (~114 000 треків), завантажуємо його в
MongoDB, роблю з нього нормальну схему (не просто плаский CSV), пишу запити, трохи аналітики
і в кінці розбираюся з індексами.

- База даних: MongoDB
- Колекції: `tracks_raw` (сирі дані як є) і `tracks` (вже оброблені)
- Датасет: [Spotify Tracks Dataset на Kaggle](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset)

## Що є в репозиторії

```
scripts/
  01_load_data.py       - читає dataset.csv і кладе в tracks_raw
  02_transform.js       - робить з tracks_raw нормальну колекцію tracks
queries/
  part2_queries.js      - завдання 2, запити
  part3_aggregations.js - завдання 3, аналітика (agregation pipeline)
  part4_indexes.js      - завдання 4, індекси + explain()
requirements.txt
.env.example
```

`dataset.csv` і `.env` не залиты в гіт (датасет важить забагато, а в .env пароль).

## Як запустити

1. Треба MongoDB. Найпростіше  безкоштовний кластер на MongoDB Atlas, або підняти локально
   через Docker:
   ```
   docker run -d --name mongo-nosql -p 27017:27017 mongo:7
   ```
2. Для .js файлів треба mongosh (`brew install mongosh`).
3. Ставимо пітонячі залежності:
   ```
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```
4. Качаємо dataset.csv з Kaggle, кладемо в корінь проєкту.
5. Копіюємо `.env.example` в `.env` і вписуємо свій MONGO_URI.

Далі по порядку (кожен наступний крок залежить від попереднього):

```
python scripts/01_load_data.py
mongosh "$MONGO_URI" --file scripts/02_transform.js
mongosh "$MONGO_URI" --file queries/part2_queries.js
mongosh "$MONGO_URI" --file queries/part3_aggregations.js
mongosh "$MONGO_URI" --file queries/part4_indexes.js
```

Скрипти можна запускати повторно, вони самі чистять/перезаписують колекції, нічого не
задублюється.

## Що я зробив зі схемою

CSV-рядок дуже плаский, тому в `02_transform.js` я:

- зробив з поля `artists` (рядок типу `"A;B"`) нормальний масив `["A", "B"]`
- зібрав 12 аудіо-полів (danceability, energy, tempo і т.д.) в один вкладений об'єкт
  `audio_features`, щоб на верхньому рівні не було каші
- додав `duration_sec` (просто ms поділити на 1000)
- додав `popularity_tier`: high / medium / low, залежно від popularity

Після очистки лишилось 113 999 треків (один рядок відкинув, бо там не було виконавця).

### Чому так

**Чому audio_features окремим об'єктом?** Бо це 12 полів, які логічно про одне й те саме 
"звукові характеристики" треку. Так зручніше  можна взяти весь блок одним полем, і на
верхньому рівні лишається тільки головне (назва, виконавці, жанр). Мінус  якщо треба лізти в
одне конкретне поле, шлях довший (`audio_features.tempo` замість просто `tempo`).

**Чому artists  масив, а не рядок?** Бо в треку може бути кілька виконавців (колаборація), і
в масиві це шукати нормально: `db.tracks.find({ artists: "ZAYN" })` знайде точно, а через
рядок довелось би городити regex і ще й помилково зловити щось типу "Drake Bell" замість
"Drake". Ще масив зручний для `$unwind`, коли рахуємо статистику по кожному артисту окремо.

**$out vs $merge.** Обидва пишуть результат агрегації в колекцію. `$out` повністю переписує
колекцію заново (тому я його і взяв  скрипт повинен бути idempotent і будувати `tracks` з
нуля кожного разу). `$merge` натомість дописує/оновлює існуючу колекцію, не стираючи те що
там було  це для випадків коли треба тільки долити нові дані.

## Завдання 2  запити

Файл `queries/part2_queries.js`.

1. **Треки для вечірки**  danceability > 0.7 і energy > 0.7, тривалість 3-5 хв. Знайшлось
   7 311 треків.
2. **Виконавці, у яких всі треки популярні**  беру виконавців з ≥3 треками і min_popularity
   ≥ 60, сортую по середній популярності. Топ там Harry Styles, Olivia Rodrigo і т.д.
3. **Незвичні треки за темпом**  для кожного жанру рахую середній темп і стандартне
   відхилення, і виводжу треки, у яких темп більше ніж mean + 2*stdDev.
4. **Музика для фону/роботи**  тихі (loudness < -10), без вокалу (instrumentalness > 0.5),
   без слів (speechiness < 0.1) і без explicit. Знайшлось 9 324 треки.

Пару теоретичних питань, які там питали:

- `$unwind` розкладає масив на окремі документи (якщо масив з 2 елементів  буде 2 копії
  документа, кожна з одним елементом замість масиву). Треба, щоб рахувати щось по кожному
  елементу масиву окремо, наприклад по кожному артисту.
- `$stdDevPop` vs `$stdDevSamp`  перше рахує відхилення так, ніби у нас вся популяція даних
  (ділить на N), друге  ніби у нас вибірка з більшої популяції (ділить на N-1). У мене всі
  треки жанру, які є в базі, це і є вся "популяція" для цього завдання, тому взяв `$stdDevPop`.

## Завдання 3  аналітика

Файл `queries/part3_aggregations.js`.

1. Топ-10 виконавців за середньою популярністю (мінімум 5 треків)  перші місця: Olivia
   Rodrigo, Måneskin, Lil Nas X.
2. Розбив треки по "настрою" через valence і energy: happy / angry / calm / sad. Найбільше
   вийшло happy і angry.
3. Найтанцювальніший жанр (мінімум 100 треків у жанрі)  вийшов жанр kids, потім
   chicago-house, reggaeton.

Питання: що буде якщо поставити поріг 1 трек замість 5  тоді нагору вилазять виконавці з
одним хітом (типу Quevedo), і це не дуже чесно, бо середнє по одному треку  це просто
популярність цього одного треку, ні про що не говорить. Якщо взяти поріг 50+ треків  лишаться
тільки дуже плодовиті виконавці, і в них середнє нижче, бо в великій дискографії завжди є
слабші треки.

Другий поріг (100 vs 50 для жанрів) нічого не міняє, бо в датасеті кожен жанр і так має майже
рівно 1000 треків  обидва пороги набагато менші за це число.

## Завдання 4  індекси

Файл `queries/part4_indexes.js`. Тут я дивився на `explain("executionStats")` до і після
створення індексів.

**Запит:** жанр pop + danceability >= 0.7, відсортовано за popularity.

Без індексу: COLLSCAN, перебирає всі 113 999 документів, ~75 мс.

Після того як зробив індекс `{ track_genre: 1, "audio_features.danceability": 1, popularity: -1 }`:
IXSCAN, читає тільки 354 документи, ~1 мс. Тобто різниця дуже велика.

Як зрозуміти що індекс працює  дивимось в explain: якщо є стадія `IXSCAN` (а не `COLLSCAN`) і
`totalKeysExamined` більше 0  значить індекс використовується.

Ще зробив індекс під запит для "робочої музики" (instrumentalness/speechiness/explicit) 
теж перейшло з COLLSCAN на IXSCAN.

**Про covered query (покривний запит).** Спробував запит тільки по track_genre і popularity
без проєкції  не покривний, бо документ все одно треба діставати повністю (FETCH), в індексі
не всі поля документа. Але якщо додати проєкцію тільки на ті поля, що є в індексі, і прибрати
_id  тоді запит стає покривним: стадія `PROJECTION_COVERED`, `totalDocsExamined = 0`, тобто
MongoDB взагалі не лізе в самі документи, бере все з індексу. Головне не забути прибрати _id
з проєкції  інакше все одно буде FETCH, бо _id немає в цьому індексі.
